🧩 Composición de skills

Las Skills se convierten en pipelines cuando las encadenas — la salida de una alimenta la siguiente.

Qué es:

Formas típicas de encadenar skills: secuencial, paralela y condicional; cada una tiene su propio disparador.

Por qué aprender:

Sin un estándar, reinventas el pipeline con cada feature. Los patrones con nombre aceleran la decisión.

Conceptos clave:

Pipeline, fan-out/fan-in, gate, orquestación.

Qué es:

Flujo estándar de Matt: la alineación se convierte en PRD, luego en issues y después en ciclos TDD hasta el merge.

Por qué aprender:

Es el ejemplo vivo de composición. Reproducir el flujo da resultados inmediatos.

Conceptos clave:

Handoff, contrato de salida, flujo canónico.

Qué es:

Una skill que orquesta otras skills: se usa cuando la misma secuencia se repite en varios proyectos.

Por qué aprender:

Macro demasiado pronto y abstracción prematura. Demasiado tarde y hay copy-paste de pipeline.

Conceptos clave:

Regla de tres, abstracción oportuna, skill compositora.

Qué es:

Las skills no guardan estado: CONTEXT.md es el canal de memoria entre ellas dentro del proyecto.

Por qué aprender:

Sin estado compartido, cada skill vuelve a aprender el dominio. Con CONTEXT.md, hay continuidad.

Conceptos clave:

Persistencia, contrato documental, fuente única de verdad.

Qué es:

Encadenamientos demasiado largos, skills con ámbitos superpuestos, dependencias cíclicas.

Por qué aprender:

Detectarlo pronto evita un pipeline frágil que nadie entiende.

Conceptos clave:

Acoplamiento excesivo, alcance difuso, ciclo, explosión de prompts.

Qué es:

Caso de refactorización: /zoom-out → /improve-codebase-architecture → /to-issues → /tdd → review.

Por qué aprender:

Ver la composición completa en un problema real fija el patrón en la cabeza.

Conceptos clave:

Refactor seguro, encadenamiento real, gates intermedios.

✏️ Personalizando skills

Toma la skill y hazla tuya: sin forks innecesarios y sin perder el upstream.

Qué es:

Anatomía del archivo: frontmatter YAML (nombre, descripción, activadores) y cuerpo Markdown con instrucciones.

Por qué aprender:

Si no entiendes la estructura, la personalización rompe la carga de la skill.

Conceptos clave:

Frontmatter, body, secciones obligatorias, parser.

Qué es:

Campos que determinan cuándo el agente carga la skill: frases, contextos y activadores explícitos.

Por qué aprender:

Un trigger deficiente = la skill nunca se activa o se activa siempre. Una descripción débil = el agente la ignora.

Conceptos clave:

Frase de activación, descripción, alcance, falsos positivos.

Qué es:

Las Skills tienen plantillas (PRD, ADR, issue). Editar las plantillas ajusta el resultado sin modificar la lógica.

Por qué aprender:

Personalización más barata y segura: cambias la forma, mantienes el comportamiento.

Conceptos clave:

Plantilla, contrato de salida, secciones, marcadores de posición.

Qué es:

Fork = copia independiente; override = la skill local con el mismo nombre se impone sobre la global en ese proyecto.

Por qué aprender:

El fork pierde el upstream. El override mantiene las actualizaciones. Una decisión equivocada sale cara después.

Conceptos clave:

Alcance local/global, precedencia, upstream, drift.

Qué es:

Tratar el directorio de skills como un repo: branches, PRs, revisión y changelog para los cambios.

Por qué aprender:

Sin control de versiones, la personalización se convierte en «.skill.bak.final.v2». El equipo pierde la trazabilidad.

Conceptos clave:

Skills-as-code, semver, changelog, revisión de skills.

Qué es:

Walkthrough que adapta /grill-with-docs a un dominio específico: términos, preguntas y referencias propias.

Por qué aprender:

Ver una personalización real disipa el miedo a modificar una skill "oficial".

Conceptos clave:

Ajuste al dominio, prompt local, referencias específicas, fork mínimo.

🤝 Integración con otros agentes

Claude Code, Codex, Cursor: una skill para todos, sin reescribir.

Qué es:

Cada agente carga las skills de manera diferente. Identifica qué es portable y qué es específico.

Por qué aprender:

Mantener N versiones de la misma skill es insostenible. Saber qué es común reduce las copias.

Conceptos clave:

Runtime, portabilidad, matriz de capacidades y superficie de exposición.

Qué es:

Una skill que empaqueta un SKILL.md en el formato portable y lo publica para Claude Code, Codex y otros.

Por qué aprender:

Build once, run anywhere — sin polyskill, mantienes N copias divergentes.

Conceptos clave:

Source of truth, transpile, adapter, runtime target.

Qué es:

Slash commands, hooks, MCP, permisos: cada runtime expone un subconjunto. Aprende cuáles afectan la portabilidad.

Por qué aprender:

Una skill que asume un hook de Claude Code no funciona en Codex. Mapear las brechas antes evita un debug confuso.

Conceptos clave:

Hook, MCP, slash command, permission, sandbox.

Qué es:

Exponer skills mediante un servidor MCP: cualquier agente compatible las consume sin instalarlas localmente.

Por qué aprender:

Todo el equipo usa la misma versión de la skill, con actualización centralizada.

Conceptos clave:

Servidor MCP, herramienta, manifiesto, descubrimiento dinámico.

Qué es:

Ejecutar skills en pipelines (GitHub Actions, GitLab CI): revisión, lint y actualización de documentación automatizados.

Por qué aprender:

Una skill en CI se convierte en un gate confiable. Pasas de "si te acuerdas de ejecutarla" a "siempre se ejecuta".

Conceptos clave:

Pipeline, gate, agente headless, artefacto, idempotencia.

Qué es:

Workflow que activa /tdd en los PR nuevos: el agente genera una prueba que falla, implementa la solución y crea un commit.

Por qué aprender:

El caso práctico cierra la ruta: todo lo aprendido funciona sin que tengas que abrir el IDE.

Conceptos clave:

Workflow YAML, secret, agent runner, automatización de PR.
