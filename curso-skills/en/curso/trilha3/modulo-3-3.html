🌐 Cross-runtime: the problem

You write a skill for Claude Code. Works perfectly. Then your colleague uses Codex and asks: "how do I run this here?". Short answer: doesn’t run. Long answer: each agent has its own syntax — frontmatter, tool format, and permission system. Copying and pasting isn't enough.

💡 Tip

Skills are executable documentation. The logic is the same in any runtime — what changes is the envelope: how the agent loads, activates, and calls tools. Solving the envelope is the job.

✓ Portable format (single source)

  • ✓Write once in a neutral format
  • ✓The build emits versions for each runtime
  • ✓One command propagates the change to everyone
  • ✓Tests run against the source, not copies

✗ Copy-paste between runtimes

  • ✗3 copies diverge in 2 weeks
  • ✗Bug fixed in one place, forgotten in the others
  • ✗Frontmatter broken by the wrong runtime
  • ✗There's no way to test consistency
2

📦 polyskill — portable format

The skill polyskill (present in the repo) solves the envelope problem. You write a single source and it emits builds specific to each runtime. Think of it as "Babel for skills."

🗂️ Typical structure of a polyskill 

minha-skill/
├── source.md              # fonte única (neutra)
├── polyskill.config.json  # mapeamento de tools
├── claude-code/           # build pra Claude Code
│   └── SKILL.md           # frontmatter + Read/Edit/Bash
├── codex/                 # build pra Codex
│   └── skill.yaml         # frontmatter Codex + read_file/write_file
└── tests/
    └── snapshot.test.ts   # garante paridade entre builds

⚡ Automatic translation

O polyskill creates three essential translators:

  • →Frontmatter: name/description/tools mapped to each runtime
  • →Tools: Read ↔ read_file, Bash ↔ shell
  • →Activation: Skill tool (Claude Code) vs activate_skill (Codex)

Practical advantage: you edit a paragraph in the single source, run polyskill build and both builds come out consistent. A production bug is a git diff, not a "which copy did I fix this in again?".

🔀 Differences between Claude Code and Codex

Before porting a skill, it's worth understanding where the two differ. Spoiler: on the surface they’re the same (Markdown + frontmatter); in the details, they’re quite different.

Dimension Claude Code Codex
File tools Read, Edit, Write read_file, write_file, apply_patch
Shell execution Bash with a permission-based sandbox shell with workspace-write/read
Skill loading Skill tool (/skill-name) + description triggers automatically activate_skill explicit or prompt-triggered
Permissions Allowlist in settings.json, prompt per tool Modes (suggest / auto-edit / full-auto)
MCP support Built in, configured in ~/.claude/mcp.json Recent support, still evolving
Subagents Yes (Task tool, parallel agents) Limited — one session at a time
Slash commands Yes, ~/.claude/commands/ Yes, but a different format

The practical rule: if your skill only reads files and writes markdown, it’s trivially portable. If it orchestrates parallel subagents with hooks, will need serious adaptation — it will probably become two skills.

🔗 Calling skills via MCP

Instead of asking the other agent to understand your skill format, wrap the skill in an MCP server. Any MCP client (Claude Code, Codex, Cursor, Cline) can call it as a tool without knowing there's a skill behind it.

🛠️ Snippet: skill as an MCP endpoint 

// mcp-skills-server/index.ts
import { Server } from "@modelcontextprotocol/sdk/server/index.js";
import { readFileSync } from "fs";

const server = new Server({ name: "skills-bridge", version: "0.1.0" });

server.tool({
  name: "grill-me",
  description: "Stress-test a plan adversarially. Returns gaps and risks.",
  inputSchema: {
    type: "object",
    properties: { plan: { type: "string" } },
    required: ["plan"]
  },
  handler: async ({ plan }) => {
    const skillBody = readFileSync("./skills/grill-me/SKILL.md", "utf8");
    return runAgentLoop({ system: skillBody, user: plan });
  }
});

server.start();

Use case: skills as an API. Your skill /grill-me becomes an endpoint that any agent — or even your CI — can call via HTTP/MCP. Centralizes the logic and avoids duplication.

📊 When to use MCP vs. polyskill

  • polyskill: the skill is mainly documentation — guides the model; it doesn’t run heavy logic
  • MCP server: the skill calls external APIs, maintains state, or has code you don't want to duplicate
  • Hybrid: polyskill emits the documentation, the MCP server exposes the specialized tools

🤖 Skills in CI/CD

Skills don’t need to be interactive. In CI/CD, you run them in batch (non-interactive, with fixed input and output to a file). Useful for automatic PR reviews, docs generation, and migration validation.

✓ Works in CI

  • ✓Skills deterministic with well-defined input
  • ✓File output (markdown, JSON)
  • ✓Restricted tools (Read + Write, no unrestricted Bash)
  • ✓Timeout configured, with a fallback in case of errors

✗ Doesn't work in CI

  • ✗Skills that ask the user (clarifications)
  • ✗Skills that depend on local session state
  • ✗Skills with interactive TUIs or prompts
  • ✗Skills that take > 10min (runner timeout)

⚠️ Important Tip

Before running a skill in CI, test with --non-interactive locally. If it asks for input at any point, it will freeze in the runner — and GitHub Actions bills you for the 6h until timeout.

🧪 Practical example: /tdd in GitHub Actions

Concrete scenario: when a PR breaks tests, automatically trigger the /tdd skill. It analyzes the error, proposes a fix, and opens a commit in the PR itself. The developer wakes up the next day to a green build.

📄 .github/workflows/tdd-loop.yml 

name: tdd-loop
on:
  pull_request:
    types: [opened, synchronize]

jobs:
  run-tdd:
    runs-on: ubuntu-latest
    permissions:
      contents: write
      pull-requests: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0

      - name: Run tests (capture failure)
        id: tests
        run: npm test || echo "failed=true" >> $GITHUB_OUTPUT

      - name: Run /tdd skill
        if: steps.tests.outputs.failed == 'true'
        uses: anthropics/claude-action@v1
        with:
          skill: tdd
          input: "fix failing tests in this PR"
          allowed-tools: "Read,Edit,Bash(npm test)"
          anthropic-api-key: ${{ secrets.ANTHROPIC_API_KEY }}

      - name: Commit fix
        if: steps.tests.outputs.failed == 'true'
        run: |
          git config user.name "tdd-bot"
          git config user.email "bot@example.com"
          git add -A
          git commit -m "fix: /tdd auto-repair" || exit 0
          git push
1

Trigger in the PR

Run on each opened e synchronize (new commits)

We capture the flow from the start—we don’t wait for the developer to ask for help.

2

Run tests and detect failures

Output failed=true serves as a condition for the next steps

Only activates the skill if something actually broke — doesn't waste API quota.

3

Invoke /tdd with restricted tools

allowed-tools limits it to Read, Edit, and Bash(npm test) — nothing else rm or curl

The allowlist is the seat belt. Without it, the skill would have too much power in an environment without human review.

4

Commit + push back to the PR

The fix becomes part of the PR history, attributed to the bot

The developer reviews the human’s diff and the bot’s—not a phantom patch without context.

🧩 Integration with Cursor, Aider, Continue

Cursor, Aider and Continue don’t have the native skill concept. They have rules, conventions or system prompts. The good news: a skill’s content fits these formats perfectly.

📐 Current portability status

  • Cursor: files .cursorrules accept Markdown directly from the skill (no frontmatter)
  • Aider: uses CONVENTIONS.md or --read to load context
  • Continue: config.json allows systemMessage with the skill body
  • Cline / Roo Code: accepted .clinerules in markdown

🔄 Generic adapter — emits for any agent 

// scripts/sync-skills.ts
import { readFileSync, writeFileSync } from "fs";
import { stripFrontmatter } from "./utils";

const skill = readFileSync("./skills/tdd/SKILL.md", "utf8");
const body = stripFrontmatter(skill);

// Cursor
writeFileSync(".cursorrules", body);

// Aider
writeFileSync("CONVENTIONS.md", body);

// Continue
const config = JSON.parse(readFileSync(".continue/config.json", "utf8"));
config.systemMessage = body;
writeFileSync(".continue/config.json", JSON.stringify(config, null, 2));

console.log("✓ skill syncronized to Cursor / Aider / Continue");

Limitation: agents without The skill concept loads the content all the time (with no dynamic activation). For short skills, that’s fine. For long skills, consider breaking them into smaller rules specific to each context.

🎼 Skills + MCP servers

The most powerful combination today: the skill orchestrates; the MCP server executes. The skill guides the model through the when e how; the MCP server provides specialized tools (DB, GitHub, Figma, Slack).

🏗️ Composition architecture 

┌──────────────────────────────────────────────────────────┐
│                      USUÁRIO                              │
│                  "/release-notes v2.3"                    │
└────────────────────────┬─────────────────────────────────┘
                         │
                         ▼
┌──────────────────────────────────────────────────────────┐
│          SKILL: /release-notes (markdown + frontmatter)   │
│   "Quando o user pedir release notes:                     │
│    1. liste commits desde a última tag                    │
│    2. agrupe por tipo (feat/fix/chore)                    │
│    3. publique no Slack #releases"                        │
└──────┬───────────────────┬───────────────────┬───────────┘
       │                   │                   │
       ▼                   ▼                   ▼
┌──────────────┐   ┌───────────────┐   ┌──────────────┐
│ MCP: github  │   │ MCP: linear   │   │ MCP: slack   │
│ list-commits │   │ get-issues    │   │ post-message │
└──────────────┘   └───────────────┘   └──────────────┘

🎯 Design principle

The skill is the script; MCP is the toolbox. A roadmap without a box is theory; a box without a roadmap is chaos.

  • →Skill describes when use each MCP tool
  • →MCP server exposes what what each tool does and its schema
  • →Model ties the two together in the how of the execution

🚧 Current limitations

Cross-runtime is a work in progress. Some things already work well; others still depend on workarounds. An honest map of the landscape:

✓ Works well cross-runtime

  • ✓Declarative skills (no code)
  • ✓Basic tools: read, write, execute
  • ✓MCP servers (open standard)
  • ✓Short skills (< 200 lines)
  • ✓Sync via polyskill / adapters

✗ Not yet / with caveats

  • ✗Parallel subagents (Claude Code only)
  • ✗Hooks (PreToolUse, PostToolUse): specific
  • ✗Slash commands with complex arguments
  • ✗Permission models differ considerably
  • ✗Skills that use experimental features of a runtime

🗺️ Roadmap (actual status, not promises)

Matt mentioned in the repo that the goal is for "every course skill should run in at least Claude Code and Codex". Today (2026), this applies to the 80% of simpler cases. Skills that depend on parallel subagents or heavy hooks are still runtime-specific.

Trend: standardization will come from MCP, not a universal skill format. If your skill is mainly a system prompt + tools, it’s already portable today.
